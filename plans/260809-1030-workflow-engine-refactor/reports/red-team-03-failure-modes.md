phase-03: **CRITICAL — TOCTOU race trong executeTransition.** Plan phase-03:143-167: đọc `prisma.case.findUniqueOrThrow` NGOÀI transaction, dùng `currentStatus` gọi `tryTransition()`, rồi mở `prisma.$transaction()` để write. Giữa read và write có race window. VD: user submit revision (T9, `waiting_user` → `supporter_working`) + supporter gửi request_info lại (T8, `supporter_working` → `waiting_user`) đồng thời. Cả 2 đọc `waiting_user` → pass guard → cả 2 vào tx — kết quả bất định, không optimistic lock. `completeCaseUseCase` hiện tại cũng có bug này (:11 đọc ngoài tx → :27 mở tx) — plan tái tạo anti-pattern thành cổng chung. **Fix:** chuyển toàn bộ L2-L4 vào 1 transaction duy nhất: `prisma.$transaction(async tx => { const caseRecord = await tx.case.findUniqueOrThrow(...); const result = tryTransition(...); if (result === null) throw; /* L4 actions */ })`. Hoặc thêm `version_no` column optimistic lock (WHERE version_no = currentVersion, increment mỗi transition).

phase-03: **HIGH — AppError constructor mismatch — error object hỏng.** Plan dùng `new AppError(400, "message")` / `new AppError(501, "message")` (2-arg). Code thực tế `shared/domain/app-error.ts`: `AppError(status, code, message, details?)` — 3 args bắt buộc. 2-arg của plan sẽ gán "message" vào `code` field, `message` undefined → FE nhận `{code: "...", message: undefined}` → UI không hiển thị text. **Fix:** `new AppError(400, "INVALID_TRANSITION", "message")`.

phase-02: **HIGH — restoreMachine crash với DB state không hợp lệ.** Plan `restoreMachine` gọi `caseMachine.resolveState({value: status, ...})`. Nếu DB có `internal_status` không phải state node (giá trị cũ từ prod, `null`, typo) → XState throw `Error: Unable to resolve state...`. Plan không có validation đầu vào. 8 state nodes khớp nhưng data prod có thể có edge case (phase-06:120-121 thừa nhận split-brain row tồn tại). **Fix:** `const VALID_STATES = new Set(['triage_pending', ...]); if (!VALID_STATES.has(status)) throw new AppError(500, 'CORRUPT_STATE', ...)`. Thêm script validation trước deploy.

phase-04: **HIGH — Song song 2 engine gây split-brain qua `update-case-status.usecase`.** Plan chuyển T5/T11 qua XState trong phase-04 nhưng `update-case-status.usecase.ts` (vẫn active, gọi symflow `applyTransition`) vẫn mount trên route. 2 code path cùng update `internal_status` — race thứ 2 chồng TOCTOU thứ 1. `update-case-status.usecase.ts` có 13 caller qua `applyTransition` (codegraph blast radius xác nhận) — nhiều hơn 5 use case plan chuyển. **Fix:** trong phase-04, remove route hoặc feature flag cho từng use case khi chuyển. Không để 2 engine cùng active cho 1 transition.

phase-05: **MEDIUM — emitEvent L5 field mismatch + await void.** Plan phase-03:207: `await emitEvent({ eventId, type, payload: { caseId, caseCode, ...} })`. Code thực tế `event-bus.ts:7`: `emitEvent(event: DomainEvent): void` — return `void`, không phải Promise. `await void` = no-op. Nguy hiểm hơn: `DomainEvent` type có thể yêu cầu `actorId` + `occurredAt` (như `update-case-status.usecase.ts:158-168`). Plan bỏ 2 field → compile fail hoặc emit thiếu field → notification listener crash. **Fix:** kiểm tra `DomainEvent` interface thực tế. Copy pattern `update-case-status.usecase.ts:157-169` (có `actorId`, `occurredAt`, `payload.caseCode`). Bỏ `await`.

phase-03: **MEDIUM — upsert strategy không khớp constraint mới.** Plan thêm `@@unique([lifecycle_unit_id, doc_type, seq])` nhưng `upsertDocumentRecordsForUnit` (document.repository.ts:224-254) dùng `buildDocumentRecordInput` → `upsertDocumentRecord` với where = `{id}` (computed ID, không phải composite unique). Khi duplicate tồn tại (2 record cùng lifecycle_unit_id + doc_type + seq khác id) → upsert theo id TẠO THÊM row mới thay vì update → vi phạm constraint mới P2002. Không có try/catch P2002 trong executor (phase-03:76-118). **Fix:** đổi `upsertDocumentRecord` dùng `where: { lifecycle_unit_id_doc_type_seq: {...} }` (composite unique Prisma) thay vì `where: { id }`. Hoặc giữ upsert-by-id nhưng merge duplicate trước.

phase-01: **MEDIUM — Migration không có fallback khi duplicate data.** Plan phase-01:63-71: SELECT check duplicates trên local. Nếu có → "script merge trước khi thêm constraint." Không có script merge cụ thể (tiêu chí gì? giữ record nào?). Migration `--create-only` đúng safety, nhưng nếu prod có duplicates không phát hiện ở local → DB từ chối constraint → deploy fail, rollback thủ công (không có down migration). **Fix:** viết merge script cụ thể (DELETE duplicate giữ latest `created_at`), test trên clone prod DB, thêm migration down file.

phase-05: **MEDIUM — Integration test không có pattern DB local.** Plan phase-05:156-196 giả định DB local test với seed. Nhưng 15 test file hiện có trong `apps/api/src/shared/infrastructure/tests/` đều unit test (không import PrismaClient, không seed) — ngoại trừ `api.test.ts` có thể. Plan không verify test infrastructure. Nếu không có DB local test → integration test không chạy → coverage chỉ là unit machine (32 assertion), không verify transaction rollback, P2002 idempotency, credit subtract thực sự. **Fix:** xác nhận `DATABASE_URL` test env trong CI/local trước khi viết integration test. Nếu không → skip integration, chỉ giữ unit test phase-05, hoặc tạo script test riêng dùng DB ảo (pglite/sqlite).
