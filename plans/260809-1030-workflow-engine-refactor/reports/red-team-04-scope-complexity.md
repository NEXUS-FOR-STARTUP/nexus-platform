# Red Team Review — Scope & Complexity Critic

**Plan:** `plans/260809-1030-workflow-engine-refactor/` (plan.md + phase-01..06)
**Date:** 2026-08-09 · Reviewer lens: Scope / YAGNI / KISS / DRY

phase-02: **HIGH — XState v5 over-engineered cho 16-transition flat state machine.** Brainstorm B1 nói "bảng v2 → XState v5 config" nhưng plan implement đầy đủ `setup({types, guards, actions}).createMachine()` với 8 state nodes + 10 guard functions + 8 action factories = ~180 dòng cho máy phẳng không hierarchical/parallel/history. Giải pháp KISS: `Map<InternalStatus, Map<TransitionName, {target, guard?}>>` lookup table ~40 dòng — bao cả `tryTransition()`, `restoreMachine()`, `getAvailableTransitions()` mà không cần dependency `xstate` 150KB. XState mang giá trị khi có compound state, actor, invoke — ở đây máy stateless + không actor + không context. **Nếu đã quyết định giữ XState** (quyết định đã chốt), ít nhất cắt giảm: bỏ `restoreMachine` (không cần snapshot — restore = tìm current state node), bỏ `tryTransition` wrapper (gọi `transition()` trực tiếp trong service), bỏ `initialCaseTransition` (T1 không phải transition — chỉ là initial state string `'triage_pending'`).

phase-03: **CRITICAL — STAGE_STATUS_MAP 1:1 mapping sai với transition table v2.** `STAGE_STATUS_MAP` map cứng `triage_pending → 'intake_pending'`. Nhưng bảng v2 T2 đích `submitted / triage_pending` — tức `triage_pending` ánh xạ tới `submitted` sau T2, nhưng tới `intake_pending` ở initial state. Một `internal_status` map tới 2 `user_facing_stage` khác nhau tùy ngữ cảnh → map 1:1 không thể đúng. Tương tự `supporter_working → 'under_review'` nhưng T9 từ `waiting_user → supporter_working` phải cho stage `revision_submitted` (bảng v2 dòng T9), không phải `under_review`. **Fix:** bỏ `STAGE_STATUS_MAP`, thêm `targetStage` vào action output của mỗi transition. Lỗi thiết kế nghiêm trọng — implement theo plan hiện tại: T2 submit xong FE hiển thị "intake_pending" thay vì "submitted".

plan-wide: **HIGH — 3 nguồn truth transition song song, plan không giải quyết DRY.** Hiện trạng: `isValidStageTransition` (case.types.ts:54 — bảng tay 6 stage) + `case-workflow.ts` (symflow — 9 transitions). Plan thêm `transition-registry.ts` (XState — 16 transitions) mà không đề cập xóa `isValidStageTransition`. Sau phase 04: 3 bảng, 2 engine sống song song (symflow + XState). 2 hàm khác nhau trả lời "từ stage A sang B được không" với kết quả khác nhau (bảng tay thiếu revision path, symflow thiếu intake path). **Fix:** ghi rõ trong plan — `isValidStageTransition` bị xóa ở phase 04 (khi `getAvailableTransitions` thay thế). Thêm task: `grep isValidStageTransition` toàn codebase → 0 caller sau phase 04.

phase-04: **MEDIUM — `getAvailableTransitions` trả blocked transitions lên FE, gây nút "ma".** Hàm trả `Object.keys(node.on ?? {})` — mọi transition khai báo trên state node, bao gồm T12-T15 (blocked guard `blocked_Q*`) → FE render nút → user bấm → lỗi 501 từ L1 `isBlockedTransition`. **Fix:** filter `transitions.filter(t => !isBlockedTransition(t))` trong `getAvailableTransitions`. Hoặc tốt hơn: đừng khai báo blocked transitions trong `states.*.on` — chỉ giữ trong `isBlockedTransition` lookup riêng. Machine chỉ chứa transition ACTIVE.

phase-05: **HIGH — Test plan over-test unit, under-test executor; estimate ảo.** 32 assertions cho 16 transitions × 2 (pass/fail) over-test — machine stateless, guard pass/fail chỉ verify config, không verify business logic. `executeAction()` switch/case 8 nhánh + async DB operations (upsert, subtractCredit, setSlaDeadline) có **0 unit test** — chỉ gián tiếp qua 4 integration test. Nếu `executeAction` sai (VD upsert gọi nhầm createDocumentRecordsForUnit thay vì upsertDocumentRecordsForUnit), integration test fail nhưng debug lâu hơn unit test. **Fix:** cắt 32 assertions xuống 16 (chỉ path hợp lệ), thêm 8 unit test `executeAction` với mock DB. 2.5h estimate ảo — DB seed riêng mất 30-60ph. Estimate thực tế: 3.5-4h.
